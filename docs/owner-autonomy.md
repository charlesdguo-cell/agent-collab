# Owner-authorized routine execution and private risk confirmation

Routine local work, dependency installation, version updates and reversible configuration changes within an authorized task are not high risk merely because they need a path outside the project or ordinary network access. The owner may opt this one installation into `executionMode: owner-autonomy`; the bridge supplies full-access thread policy with on-request approval and an explicit high-risk confirmation instruction. This does not edit global Codex configuration or override administrator requirements. Existing installations retain inherited policy until that owner opts in.

Before irreversible important-data loss, sensitive disclosure, financial transactions, expanded security authority or destructive production impact, the Agent returns a concrete `confirmation` instead of executing it. The coordinator persists the action and sends it privately to the configured owner. Only an authenticated human reply in that owner's private chat, containing the specific `/confirm A-…` or `/reject A-…`, resolves it. Group messages, bot messages, other humans and replayed decisions do not grant authority. A decision resumes the original task/session with the exact scope; a rejection is not rewritten as assent. The model must assess business risk: filesystem access alone is not a complete risk classifier.

Native command/file approval requests also use the private owner path and await an explicit single-action decision. These preserve the currently suspended tool call instead of starting a second job. Interrupt/restart invalidates native approvals; a stale yes cannot authorize a different future command. The normal 15-minute model-turn budget still bounds a native pending prompt; semantic `confirmation` is persisted after the turn and can be answered after restart. MCP forms, permission-set grants and unknown dynamic tools remain non-grant unless implemented explicitly; no fabricated answers or blanket approval callback.

## Upgrade lifecycle

The public installer supports staging without activation (`--stage-only`) and configured-service upgrade (`--activate-upgrade`). It starts a separate maintenance process which sets draining, waits for active jobs, retains a SQLite write lock across the final idle check and shutdown (including older runtimes), snapshots state/config/plist, switches the versioned runtime, and restores the prior selection on activation failure. Pending tasks are preserved. A dead maintenance process is detected by the new runtime so it does not leave scheduling permanently drained. Inspect `maintenance-status.json`; a queued request is not a successful upgrade.

Use the actual home/root/service label for the installation. A process cannot use this feature to bypass its inherited OS sandbox. Old sandboxed installations need a one-time owner-authorized independent terminal bootstrap with `--activate-upgrade --enable-owner-autonomy`; after that, the new policy and maintenance flow handle ordinary upgrades. Never substitute another person's machine or stop an active model turn to claim success.

After this version is installed, authenticated private owner commands `开启自主执行` / `恢复默认执行权限` persist the per-installation mode for future turns; group/bot commands cannot change it.
