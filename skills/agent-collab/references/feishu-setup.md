# Feishu setup on the installing computer

Use an existing dedicated self-built application where provided. A webhook-only custom group bot cannot receive the required events. Never put App Secret in chat or shell arguments.

1. Open https://open.feishu.cn/app in the user's local browser. If unavailable, have the user open it. Reuse login; ask only for unavoidable human login/organization authorization. Create an enterprise self-built app if none exists, enable its Bot capability, and name it to identify its owner.
2. In Permissions, enable application-identity scopes needed here: `im:chat.members:read` (group participant identity), `im:chat.announcement:read` (read and remember the group announcement), `im:message:send_as_bot` (send), `im:message:readonly` (history), `im:message.p2p_msg:readonly` (private pairing), `im:message.group_at_msg.include_bot:readonly` (human and bot @mentions), and `im:message.group_msg` (unmentioned replies inside consultation topics). Group-message access may require organization approval. Do not request user-identity send permissions merely to automate pairing. Use the actual platform error to identify any missing scope, not a broad all-permissions grant.
3. Publish the app/version and set availability to the participating users/group according to the organization's controls. In the Feishu group, add this application bot. Group ID must be `oc_...` or a group link containing `openChatId`; a message URL isn't interchangeable.
4. Launch the local setup page, enter App ID/Secret ONLY in that page, and select verify/pair. Its temporary WebSocket listener can establish the connection needed to save long-connection subscriptions. In the application console's Events and Callbacks, choose long connection and subscribe to `im.message.receive_v1`; optionally subscribe to `im.chat.member.bot.added_v1` to refresh the announcement on group-entry events. Startup and job-driven refresh still work without that optional event. If saving says no connection, keep setup running, verify credentials, and retry after a connection is established. Publish permission/event changes if the console requires it.
5. The user sends the displayed short-lived pairing text in a PRIVATE chat to that exact bot. Wait for the local page to show paired. If it expires, generate a new code; don't send it to the group or fabricate open_id values. Set local project, group and runtime, then save. Setup exits in installer mode; check its exit and configuration before continuing.
6. Run doctor and install/start the local service. The installer is not responsible for release QA. Offer ordinary use via @bot in the group; diagnose an actual failure with troubleshooting.md. Local ready status proves prerequisites, not a live group conversation.

No agent/browser can bypass administrator approval. Explain the exact pending approval to the user and preserve installation state. Credentials and pairing may require user action, but not the maintainer.

Official references: https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/message/list and https://aily.feishu.cn/hc/1u7kleqg_uv8vbhxz . Scope names and console layout should be checked against the actual application's current console.

Bot event contract: `sender_type=bot` on receive_v1; message-history endpoints may use `app`. Normalize both, never treat either as a human. Official receive documentation: https://open.feishu.cn/document/server-docs/im-v1/message/events/receive.md . Bot history, when needed, requires `im:message.group_msg.include_bot:read`; avoid granting it just for addressed bot events.
